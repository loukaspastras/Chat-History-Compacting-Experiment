Διαχείριση Ιστορικού Συνομιλίας & Prompt Caching

Πείραμα μέτρησης του trade-off μεταξύ κόστους, cache hit rate και ακρίβειας ανάκλησης σε τρεις στρατηγικές διαχείρισης ιστορικού.

Μοντέλα: gpt-4o (OpenAI) & claude-haiku-4-5 (Anthropic) · 100 ερωτήσεις/συνομιλία · MCQ εξέταση μνήμης 12 ερωτήσεων · Μάιος 2026

Με δύο λόγια (TL;DR)

  • Cache hit = ταίριασμα prefix. Οποιαδήποτε αλλαγή έστω και ενός byte στο prefix ακυρώνει το cache από εκείνο το σημείο και μετά. Σταθερό prefix → φθηνά reads· μεταβλητό prefix → πληρώνεις πλήρη τιμή.
  • Το append-only (Στρατηγική Α) είναι το ταβάνι ακρίβειας (100%) και έχει το υψηλότερο cache hit, αλλά το context μεγαλώνει γραμμικά → σε μακριές συνομιλίες το κόστος εκτοξεύεται.
  • Το compaction (Στρατηγική C) με σωστό n αξίζει: στο Haiku, το n=40 πιάνει 100% ακρίβεια με φραγμένο context — ισοφαρίζει το append-only χωρίς το γραμμικό κόστος.
  • Το naive pruning (Στρατηγική B) ΔΕΝ αξίζει: ξεχνάει τα πρώτα/μεσαία facts (0–17%) χωρίς να είναι φθηνότερο. Κυριαρχείται (dominated) από τις άλλες δύο.
  • Tool calls & RAG αλλάζουν δραματικά την εικόνα: τα tools μπαίνουν πρώτα στο prefix, οπότε ένα δυναμικό tool-set ή RAG context στην αρχή «σπάει» όλο το cache. Ο κανόνας: σταθερά μπροστά, μεταβλητά πίσω.

1. Τι δοκιμάσαμε

Όταν ένας LLM agent κρατάει μια μακριά συνομιλία, ολόκληρο το ιστορικό ξαναστέλνεται σε κάθε γύρο. Ο τρόπος που διαχειρίζεσαι αυτό το ιστορικό ελέγχει ταυτόχρονα τρία πράγματα: πόσο πληρώνεις, πόσο καλά δουλεύει το prompt caching, και πόσο «θυμάται» το μοντέλο. Στήσαμε ένα ελεγχόμενο end-to-end πείραμα για να μετρήσουμε αυτό ακριβώς το τριπλό trade-off.

Οι τρεις στρατηγικές

ΣτρατηγικήΣυμπεριφοράΛογική
A Append-onlyΔεν κόβει ποτέ· κάθε γύρος προστίθεται στο τέλος.Σταθερό prefix → υψηλό cache hit, αλλά context (και κόστος) που μεγαλώνει γραμμικά.
B Front-slash (pruning)Κρατάει το πολύ n μηνύματα· όταν ξεπεραστεί, πετάει το παλαιότερο.Φράζει το context, αλλά το «παράθυρο» μετακινείται κάθε γύρο → χαλάει το cache της ουράς και ξεχνάει παλιά facts.
C CompactionΑφήνει το ιστορικό να φτάσει τα n μηνύματα, μετά το συνοψίζει με ένα γρήγορο μοντέλο και αντικαθιστά το raw block με μια πυκνή περίληψη.Φράζει το context και διατηρεί τα facts, ξαναχτίζοντας ένα σταθερό cache baseline.

Σχεδιασμός πειράματος

  • Setup: ένα μεγάλο σταθερό system prompt (> 4096 tokens, ώστε να ενεργοποιείται το cache του Haiku από τον πρώτο γύρο) δίνει εντολή στο μοντέλο να κάνει «συνέντευξη» ρωτώντας 100 ερωτήσεις, μία-μία.
  • Συνέντευξη: το script παίζει έναν σταθερό φανταστικό χαρακτήρα και απαντά και στις 100 ερωτήσεις. Κάθε απάντηση κουβαλάει ένα μοναδικό fact. Η στρατηγική επεξεργάζεται το ιστορικό σε κάθε γύρο.
  • Εξέταση: ένα MCQ τεστ μνήμης 12 ερωτήσεων ελέγχει facts απ’ όλο το εύρος (με έμφαση στην αρχή/μέση — εκεί ακριβώς που χτυπάει το pruning/compaction). Το μοντέλο απαντά σε αυστηρό JSON· η βαθμολόγηση είναι ντετερμινιστική (ακριβές ταίριασμα γράμματος, χωρίς LLM judge).

Κάθε API call καταγράφηκε σε SQLite: πλήρης ανάλυση tokens (uncached / cached / cache-write / output), υπολογισμένο κόστος, και ολόκληρο το request/response payload.

2. Πότε θεωρείται κάτι «cache hit»; — Οι κανόνες

Το prompt caching και στους δύο providers είναι prefix cache. Υπάρχει ένας θεμελιώδης κανόνας απ’ τον οποίο απορρέουν όλοι οι άλλοι:

Ο μοναδικός νόμος: Το cache δουλεύει με ταίριασμα προθέματος (prefix). Οποιαδήποτε αλλαγή — έστω κι ένα byte — οπουδήποτε μέσα στο prefix ακυρώνει το cache για όλα όσα έρχονται μετά. Το cache key προκύπτει απ’ τα ακριβή bytes του rendered prompt μέχρι κάθε breakpoint.

Σειρά rendering & πού «κουμπώνει» το cache

Το prompt χτίζεται πάντα με τη σειρά: tools → system → messages. Άρα ό,τι είναι σταθερό πρέπει να μπαίνει μπροστά, κι ό,τι αλλάζει (timestamps, per-request IDs, retrieved chunks, η τρέχουσα ερώτηση) πίσω, μετά το τελευταίο σημείο που θέλεις να κάνει cache.

Ελάχιστο μέγεθος για να «πιάσει» το cache

Provider / ΜοντέλοΕλάχιστο prefixΣημείωση
OpenAI (π.χ. gpt-4o)1.024 tokensΑυτόματο caching· κάτω απ’ αυτό απλώς δεν γίνεται cache (σιωπηλά).
Anthropic — Opus 4.x / Haiku 4.54.096 tokensΓι’ αυτό φτιάξαμε το system prompt μας να ξεπερνά τα 4096 (μετρήθηκε στα 4.273).
Anthropic — Sonnet 4.62.048 tokensΔιαφέρει ανά μοντέλο.
Anthropic — Sonnet 4.5 / 3.71.024 tokensΈνα prompt 3K tokens κάνει cache στο Sonnet 4.5 αλλά όχι στο Haiku 4.5.

Πραγματικό εύρημα του πειράματός μας: με το αρχικό system prompt στα ~1.245 tokens, το cache_read του Anthropic έβγαινε σιωπηλά μηδέν. Μόνο αφού το μεγαλώσαμε > 4096 ενεργοποιήθηκε το cache (cache reads ~4.277 tokens/κλήση). Το «δεν κάνει cache» δεν δίνει error — απλώς πληρώνεις πλήρη τιμή χωρίς να το καταλάβεις.

Μηχανισμός ανά provider

OpenAI — αυτόματο

  • Γίνεται μόνο του σε prefix ≥ 1024 tokens.
  • prompt_cache_key: σταθεροποιεί το routing (ίδιο key → ίδιο μηχάνημα → πιο πιθανό hit).
  • prompt_cache_retention: "24h": κρατάει το cache ζεστό μεταξύ γύρων.
  • Έκπτωση: cached input ≈ 0.5× (gpt-4o: $1.25 vs $2.50 / 1Μ).
  • Έλεγχος: usage.prompt_tokens_details.cached_tokens.

Anthropic — ρητό (explicit)

  • Βάζεις cache_control: {"type":"ephemeral"} σε blocks — έως 4 breakpoints.
  • TTL: 5 λεπτά (default) ή 1 ώρα.
  • Κόστος: cache read ≈ 0.1×, cache write ≈ 1.25× (5′) ή 2× (1ω).
  • «Παράθυρο» αναζήτησης: 20 blocks προς τα πίσω — σε agentic loops με >20 tool blocks/γύρο σπάει το incremental cache.
  • Έλεγχος: usage.cache_read_input_tokens / cache_creation_input_tokens.

Τι σου «σπάει» σιωπηλά το cache (silent invalidators)

  • Αλλαγή στα tools (προσθήκη/αφαίρεση/αναδιάταξη): τα tools είναι στη θέση 0 → ακυρώνεται ολόκληρο το cache.
  • Αλλαγή system prompt ή μοντέλου (τα caches είναι ανά μοντέλο).
  • Μη-ντετερμινιστικό serialization: json.dumps χωρίς sort_keys, iteration πάνω σε set.
  • Δυναμικό περιεχόμενο στην αρχή: datetime.now(), UUID, session/user ID μέσα στο system prompt.
  • Concurrency: N παράλληλα requests με ίδιο prefix κάνουν όλα miss — κανένα δεν προλαβαίνει να διαβάσει αυτό που γράφουν τα άλλα. (Το είδαμε στο πείραμα: η παραλληλία ανέβασε τα cache writes.)

3. Αξίζει το compacting / pruning, ή σου χαλάει το performance;

Η σύντομη απάντηση: εξαρτάται απ’ το μήκος της συνομιλίας, και τα δύο δεν είναι το ίδιο πράγμα.

Pruning (front-slash) — όχι, μην το κάνεις. Στα πειράματά μας το naive pruning είναι dominated: ξεχνάει τα πρώτα/μεσαία facts (ακρίβεια 0–17%) χωρίς να γλιτώνει χρήματα — και ταυτόχρονα χαλάει το cache της ουράς της συνομιλίας, αφού το παράθυρο μετακινείται κάθε γύρο. Πληρώνεις την «ποινή της λήθης» χωρίς αντάλλαγμα σε κόστος.
Compaction — ναι, με σωστό n. Στο Haiku, το C/n=40 ισοφάρισε το append-only στο 100% ακρίβεια ($0.123) κρατώντας το context φραγμένο. Το όφελος μεγαλώνει όσο μακραίνει η συνομιλία: το append-only μεγαλώνει γραμμικά (στο όριο γίνεται απαγορευτικό), ενώ το compaction μένει φραγμένο.

Δύο προειδοποιήσεις για το compaction:

  • Πολύ επιθετικό n = κακό: το C/n=10 έπεσε στο 33%. Όταν συνοψίζεις πολύ συχνά, η περίληψη ξανα-συνοψίζεται επανειλημμένα (lossy re-summarization) και χάνονται λεπτομέρειες.
  • Έχει δικό του κόστος: κάθε compaction είναι μια επιπλέον κλήση σε γρήγορο μοντέλο. Στα νούμερά μας ήταν μικρό (~$0.02–0.12), αλλά υπάρχει.

Κανόνας: για σύντομες συνομιλίες κράτα append-only (πιο απλό, φθηνό, τέλεια μνήμη). Για μακριές/agentic ροές, compaction σε μέτριο n. Pruning σχεδόν ποτέ.

4. Πώς αλλάζει η εικόνα με tool calls & RAG

Το πείραμά μας ήταν «καθαρή» συνομιλία. Μόλις μπουν tools και RAG, αλλάζουν τα δεδομένα — και κυρίως το caching.

Tool calls

  • Τα tools είναι στη θέση 0 του prefix. Αν αλλάζεις δυναμικά το tool-set ανά request, ακυρώνεις ολόκληρο το cache κάθε φορά. Κράτα το tool-set σταθερό και ταξινομημένο ντετερμινιστικά (π.χ. sort by name).
  • Τα tool results φουσκώνουν το context γρήγορα. Σε agentic loops, κάθε tool_use/tool_result ζευγάρι προστίθεται στο ιστορικό — το context μεγαλώνει πιο γρήγορα κι απ’ ό,τι στη δική μας συνομιλία. Εδώ το compaction / context-editing γίνεται ακόμα πιο πολύτιμο.
  • Όριο 20 blocks (Anthropic): αν ένας γύρος προσθέσει >20 content blocks (συνηθισμένο με πολλά tool calls), το επόμενο breakpoint δεν «βρίσκει» το προηγούμενο cache. Λύση: ενδιάμεσα breakpoints κάθε ~15 blocks.
  • Tool search: ανακαλύπτει tools δυναμικά προσθέτοντας schemas (όχι αντικαθιστώντας) → διατηρεί το cache, σε αντίθεση με το να αλλάζεις το tools array.
  • Αλλαγή μοντέλου στη μέση: για ένα φθηνό υπο-task (π.χ. summarization, όπως κάναμε εμείς με Haiku), μην αλλάζεις το μοντέλο του κύριου loop — σπάει το cache. Κάνε spawn ξεχωριστό sub-agent.

RAG (Retrieval-Augmented Generation)

  • Το retrieved περιεχόμενο αλλάζει ανά query → είναι εγγενώς μη-cacheable. Αν το βάλεις μπροστά (πριν το σταθερό σου περιεχόμενο), ακυρώνεις και ό,τι ήταν cacheable από κάτω. Βάλ’ το πάντα μετά το σταθερό cached prefix.
  • Σταθερή knowledge base: αν επαναχρησιμοποιείς το ίδιο μεγάλο έγγραφο σε πολλά queries, βάλ’ το με cache_control — εκεί κερδίζεις. Δυναμικά top-k chunks ανά query → δεν κερδίζεις cache, μόνο πληρώνεις.
  • Η «λήθη» γίνεται κρίσιμη: ένα RAG σύστημα πρέπει να κρατάει στο context τα σχετικά retrieved chunks. Είδαμε ότι όταν η πληροφορία κοπεί (Στρατηγική B), το μοντέλο τίμια απαντά «τίποτα απ’ τα παραπάνω» — δεν μαντεύει. Αν κόψεις λάθος chunk, το RAG απλώς δεν ξέρει.
  • Πρακτικά: cache το σταθερό (system + tools + σταθερά docs), κράτα τα per-query retrieved στο τέλος, και για μακριές συνεδρίες συνδύασε με compaction του ιστορικού διαλόγου (όχι των retrieved — αυτά είναι ήδη εφήμερα).

Ανάλυση — τι μας λένε τα νούμερα

Α (append-only): το ταβάνι. 100% ακρίβεια και στα δύο μοντέλα, με το υψηλότερο cache hit (σταθερό prefix → σχεδόν όλα reads). Στους 100 γύρους είναι και το φθηνότερο στο Haiku — το context δεν πρόλαβε να μεγαλώσει αρκετά ώστε το overhead του compaction να αξίζει. Όμως το κόστος μεγαλώνει γραμμικά: σε χιλιάδες γύρους, το Α γίνεται απαγορευτικό.

B (pruning): η «λήθη» χωρίς ανταμοιβή. Δύο σημαντικά μοτίβα:

  • Η ακρίβεια ανεβαίνει με το n (0% → 0% → 17%): όσο μεγαλώνει το παράθυρο, καλύπτει πιο πρόσφατους γύρους, αλλά ποτέ δεν φτάνει τα πρώτα facts που ζητάει η εξέταση.
  • Το cache hit ΠΕΦΤΕΙ με το n (94% → 86% → 81%): όσο μεγαλώνει το (μη-cacheable, γιατί ολισθαίνει) παράθυρο, «αραιώνει» το cached σταθερό system prompt. Δηλαδή το B πληρώνει περισσότερο για να θυμάται λιγάκι παραπάνω.
  • Το 0% είναι τίμια αποχή, όχι τύχη: το μοντέλο επιλέγει «τίποτα απ’ τα παραπάνω» όταν δεν έχει το fact — γι’ αυτό πέφτει κάτω απ’ το ~25% της τυχαίας μαντεψιάς. Καλό σημάδι ευθύτητας, κακό για ανάκληση.

C (compaction): ο νικητής με μέτρο. Το n=40 ισοφαρίζει το Α (100%) με φραγμένο context και 98.2% cache. Το n=10 καταρρέει στο 33% (υπερβολικά συχνή, lossy σύνοψη). Το n=100 πιάνει 83% (2 λάθη στις 12 — μέσα στο εύρος θορύβου). Το cache hit του C είναι σταθερά υψηλό (95–99%) γιατί η περίληψη ξαναφτιάχνει σταθερό prefix.

Διασταυρωτικά (cross-provider): το gpt-4o κοστίζει ~9× το Haiku στο append-only ($0.894 vs $0.097) — η επιλογή μοντέλου κυριαρχεί στο κόστος. Επίσης το cache του OpenAI φάνηκε λιγότερο «επιθετικό»: gpt-4o B/n=10 είχε 73.9% cache έναντι 94% του Haiku, επειδή η ρητή στρατηγική breakpoints του Anthropic + το μεγάλο σταθερό system δίνουν υψηλότερο hit.

Pareto-βέλτιστο: για το Haiku στους 100 γύρους, το Α κυριαρχεί (φθηνότερο και ακριβέστερο). Αλλά η καλύτερη επιλογή φραγμένου context είναι το C/n=40 (100% στα $0.123) — κι αυτό είναι που θα κερδίσει σε πραγματικές, μακριές agentic συνομιλίες.

6. Πρακτικοί κανόνες (cheat sheet)

  • Σταθερά μπροστά, μεταβλητά πίσω. system + tools + σταθερά docs στην αρχή (cached)· timestamps, IDs, retrieved chunks, τρέχουσα ερώτηση στο τέλος.
  • Πάγωσε το system prompt & το tool-set. Μην ενσωματώνεις ημερομηνία/όνομα χρήστη μέσα τους· πέρνα τα ως ξεχωριστό message πιο κάτω.
  • Μέγεθος έχει σημασία: βεβαιώσου ότι το cached prefix ξεπερνά το ελάχιστο του μοντέλου (4096 για Haiku 4.5/Opus), αλλιώς πληρώνεις σιωπηλά πλήρη τιμή.
  • Επιβεβαίωσε με metrics: αν το cache_read είναι 0 σε επαναλαμβανόμενα ίδια prefixes, ψάξε silent invalidator.
  • Σύντομη συνομιλία → append-only. Μακριά/agentic → compaction σε μέτριο n. Pruning → σχεδόν ποτέ.
  • Tool-heavy: σταθερό, ταξινομημένο tool-set· tool search αντί για swap· πρόσεξε το όριο 20-blocks.

7. Μεθοδολογία & επιφυλάξεις

  • Ντετερμινιστική βαθμολόγηση, αλλά η επιλογή του μοντέλου είναι στοχαστική (το temperature δεν καρφώθηκε) και η εξέταση έχει 12 ερωτήσεις — μικρές διαφορές είναι θόρυβος.
  • Concurrency: κάποια configs μετρήθηκαν υπό παράλληλη εκτέλεση, που προσθέτει θόρυβο στο cache hit %.
  • gpt-4o ημιτελές: ο λογαριασμός OpenAI εξάντλησε το quota (το tier των 30k TPM έκανε και την υψηλή παραλληλία αντιπαραγωγική — το Anthropic, αντίθετα, παραλληλίστηκε καθαρά). Συμπληρώνεται με python run_matrix.py --resume.
  • Πλήρης ιχνηλασιμότητα: κάθε κλήση καταγράφηκε με πλήρες payload σε SQLite· το results/report.md είναι η μηχανο-παραγόμενη σύνοψη.
